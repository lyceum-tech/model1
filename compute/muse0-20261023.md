# Lyceum — Run:ai + Dynamo Test Platform and Migration Plan

## Goal

Prove, on a disposable AWS test platform with the minimum GPUs, whether `Run:ai (hardware/scheduling/governance) + Dynamo (inference)` should manage the new 8-GPU-per-machine datacenter — without breaking Lyceum's customer contracts. Deliver: (1) the AWS test stack, (2) a step-by-step migration of the current stack onto it, (3) a SWOT of Run:ai+Dynamo grounded in this repo, (4) a lower-complexity alternative at equal reliability, tested head-to-head.

## Success Criteria

- One `terraform apply` + GitOps sync brings up the AWS platform; one command tears the GPU nodes down to zero cost.
- An existing Lyceum model (DeepSeek-V4-Flash or GLM-5.3-Flash, already Dynamo-templated) serves OpenAI-compatible chat (sync + streaming + tool calls) through the *unmodified* customer path: `lyceum-cli` / OpenAI SDK → InferenceProxy → Dynamo frontend, with Croesus billing events emitted.
- A dedicated deployment creation via `deployment_controller` results in a `DynamoGraphDeployment` scheduled *by Run:ai/KAI* onto an 8-GPU node as one gang — no half-placed workers holding GPUs.
- Kill-a-worker, kill-a-node, and scale 1→2 replicas are demonstrated with no dropped healthy deployment.
- A written go/no-go: Run:ai+Dynamo vs the lean alternative, with measured TTFT/throughput/cost and operator-hours, not vendor claims.

## Current Stack — What the Repo Actually Shows

Do not migrate the wiki diagram; migrate the code. Two inference paths coexist and only one should survive onto the test platform:

| Layer | Today (code) | Keep / Retire |
|---|---|---|
| Customer API | `lyceum/README.md`: `app/` FastAPI Gateway + `lyceum-cli`; being dismantled, Iris logic moving into Iris services | Keep API shapes; do not port more into `/app` |
| Inference edge | `lyceum/iris/inference_proxy` (Go, Cloud Run): auth `lk_*`, model catalogue, Croesus spend gate/spool, Chat/Responses/Anthropic translation, direct HTTP dial to deployment endpoints (`provider/iris`, `openaicompat`), plus external providers (Nebius/TensorX/Melious) | **Keep as the only customer edge** |
| Control plane (new) | `lyceum/iris/deployment_controller`: builds either a `StatefulSet` (vLLM + worker sidecar) **or** a `DynamoGraphDeployment` (`nvidia.com/v1beta1`) from per-model templates in `internal/k8smanifest/templates/`; `lyceum/iris/iris_operator` reports pod→replica status | **Keep; this is the migration seam** |
| Control plane (legacy) | `lyceum/stream_execlet` Streamer/Execlet + RabbitMQ queue + Redis poll + Python `inference_worker` sidecar (still described in `lyceum/docs/wiki/docs/iris/overview.md`) | **Retire from test platform** — Dynamo graphs have no worker sidecar; resurrecting RabbitMQ poll would test the wrong system |
| Node supply | Hydra autoscaler (`lyceum/infra/services/hydra-autoscaler`) rents VMs (Verda/Prime Intellect/Atlas/UpCloud) and joins them to k3s; labels/taints `lyceum.technology/pool=dedicated`, `reserved-org` | Replaced *in the new DC* by owned nodes; Run:ai must not double-manage what Hydra/controller already do |
| Cluster | Ansible `k3s_server` role: k3s `v1.36.1+k3s1`, Cilium, GPU Operator `v25.3.4` (driver off, toolkit on, `nvidia` RuntimeClass), Dynamo Platform `1.4.2` (etcd/NATS off — K8s discovery + ZMQ), KEDA `2.20.2`, cert-manager, External Secrets, Grafana Cloud | **Template for the DC**; AWS test mirrors its Helm values, not its GCP plumbing |
| Billing/metrics | `lyceum/croesus` (Go); token usage from proxy, dedicated replica-seconds from `deployment_controller/internal/replicabilling`; MetricServer → Prometheus | Keep both meters; DGD has no worker to emit them |

Already Dynamo in production templates — this is not greenfield: e.g. `lyceum/iris/deployment_controller/internal/k8smanifest/templates/dsv4flashv2.yaml` is Frontend (`DYN_ROUTER_MODE=kv`, block-size 256) + `VllmDecodeWorker`. Known scar tissue: `lyceum/iris/model_image/_shared/dynamo_mm` carries 7 unmerged-upstream patches (N² multimodal transfers, SIGBUS, NIXL leaks); `deployment_controller` refuses KEDA autoscaling for DGD (`ErrAutoscalingUnsupportedKind` — a ScaledObject scales a StatefulSet, a graph has none).

## Approach — Key Decisions

1. **AWS test = EKS, DC = bare-metal K8s, same Helm/GitOps.** EKS gives a managed control plane to test HA claims fast; everything above the node (GPU Operator, Run:ai, Dynamo, Iris charts) must be plain Helm/Kustomize so it replays on the DC's k3s/kubeadm cluster unchanged. No EKS-only APIs in the workload path.
2. **Minimum GPUs, two tiers.** Always-off by default: 1× `g6e.xlarge` (1× L40S — cheapest smoke/CI node) scaled from zero, plus 1× 8-GPU node (`p4d.24xlarge` 8×A100 preferred for cost; `p5.48xlarge` 8×H100 only if quota allows) started only in a booked test window. One 8-GPU node is enough to prove gang placement, NVLink TP, and Run:ai topology; disaggregated prefill/decode across *nodes* is explicitly a Phase-2 question (see Risks).
3. **Run:ai single-cluster mode.** Control plane + cluster services in the same EKS cluster (Run:ai's documented deployment model), system nodes separated from GPU nodes by taints. Multi-cluster federation is out of scope until the DC exists.
4. **One scheduler owns GPUs.** The critical integration decision: Run:ai ships KAI Scheduler with fair-share/preemption/fractional GPU. Lyceum already encodes policy in node labels, ResourceQuotas, PDBs, and KEDA. On the test platform, KAI is the *only* GPU scheduler for `iris-workloads`; `deployment_controller` must label DGDs for KAI and stop relying on `nodeSelector` alone — or we will debug two schedulers fighting.
5. **Iris contracts frozen.** `inference_proxy`, `deployment_controller`, `iris_operator`, `croesus` deploy first, unchanged in API. Run:ai/Dynamo are substrate swaps underneath them. If a step needs a proxy API change, the step is wrong.

## Steps

### Phase 0 — Baseline (2–3 days)

1. Freeze a golden workload: one DGD model + one StatefulSet model from `k8smanifest/templates/`, fixed prompts, `aiperf`/existing `iris/dev_tools/bench` harness. Record TTFT, tok/s/GPU, cold-start on current GCP k3s.
2. Inventory the GCP couplings to sever: Cloud Run, CloudSQL, Memorystore, Secret Manager, Artifact Registry, GCP-OIDC k8s auth (`gcp:<email>` RBAC), Grafana Cloud tokens. Each gets an AWS twin or an in-cluster substitute (below).

### Phase 1 — Minimum AWS Platform (1 week)

3. Terraform (new `infra/terraform/aws/test-platform/`, Terragrunt unit to match repo convention): VPC (2 AZs), EKS (K8s ≥1.30 per Dynamo install guide), ECR mirror of Lyceum + Dynamo images, ACM cert + Route53 FQDNs (Run:ai requires LB + ingress + DNS + TLS), SOPS→AWS Secrets Manager bridge via External Secrets.
4. Node groups: `system` (3× `m7i.2xlarge` — Run:ai control plane minimum is 10 CPU/12 GB/110 GB, additive when co-located), `gpu-smoke` (g6e, min 0), `gpu-8` (p4d/p5, min 0, taint `lyceum.technology/gpu=true:NoSchedule` to mirror prod). EBS gp3 as default StorageClass (Run:ai requirement); EFS only if a test truly needs RWX — model weights stay node-local PVCs as in prod (`local-path` pattern → EBS), because shared FS for 100 GB+ weights is a cost/latency trap to evaluate, not assume.
5. GPU enablement decision, made once: EKS AL2023 accelerated AMI (driver preinstalled) + GPU Operator toolkit-only — mirroring prod's `driver.enabled=false`. Do *not* also enable operator-managed drivers; Dynamo's guide explicitly warns against provider+operator driver overlap.
6. GitOps (Flux, extending the `infra/k8s` experiment): GPU Operator → cert-manager/ESO → KEDA → Dynamo Platform (pin `1.4.2` first for parity with prod, then a separate 1.6.0 upgrade test) → Run:ai via `runai-installer` guided install → Iris services as plain Deployments (proxy behind ALB, controller, metric-server, scaler, operator in-cluster) with RDS Postgres (Croesus + Iris DBs) and ElastiCache Redis *only* where the kept code still needs it (proxy caches, scaler leader election).

### Phase 2 — Migrate Iris Step by Step (1–2 weeks, each step independently revertible)

7. **Step 1 — Edge only:** proxy on EKS proxying to an *external* provider (Nebius path). Proves auth/billing/DNS with zero GPUs.
8. **Step 2 — StatefulSet parity:** one non-Dynamo vLLM deployment via `deployment_controller` + `iris_operator` on the g6e node. Proves the k8s backend, endpoint TLS, and replica lifecycle without NVIDIA inference stack in the loop.
9. **Step 3 — Dynamo, no Run:ai scheduling:** same model as DGD with default `kube-scheduler`. Diff against Step 2 (this isolates Dynamo's value: KV-aware routing, disaggregation).
10. **Step 4 — Run:ai/KAI on:** re-schedule the DGD under KAI with a Lyceum project/department quota mapping (org → Run:ai project, dedicated pool → node pool). Prove: gang (all-or-nothing on 8-GPU node), preemption of a low-priority batch pod, fractional GPU *refused* for dedicated (whole-GPU only — fractional serving GPUs would break replica billing assumptions).
11. **Step 5 — Autoscaling truth:** DGD cannot use KEDA today. Test Dynamo Planner (SLA-driven prefill/decode scaling) against the Phase-0 baseline; if Planner underperforms or is opaque, that is a SWOT finding with data, and Step 5b wires KEDA→controller→DGD replica patching as the fallback.
12. **Step 6 — Serverless pool:** one shared serverless DGD (frontend = replica per `iris_operator` semantics) behind the proxy's model-name routing, with per-token Croesus metering verified end-to-end.

### Phase 3 — Reliability Gates (3–4 days)

13. Chaos: `kubectl delete pod` (worker, frontend), cordon+drain GPU node, AZ node loss. Pass = proxy health registry drains the endpoint, in-flight streaming requests either complete or fail with a retriable error — never a silent 200 with dropped content (the failure mode Lyceum already patches in `dynamo_mm`).

## SWOT — Run:ai + Dynamo at Lyceum

|  | Finding (repo-grounded) |
|---|---|
| **Strengths** | Dynamo already proven in Lyceum templates; KV-aware routing + disaggregated P/D directly attack TTFT/throughput on 8-GPU nodes. Run:ai gives the multi-tenant GPU governance (quota hierarchy, fair-share, preemption) that Lyceum currently hand-rolls across Hydra labels + ResourceQuotas + scaler. Single vendor for GPU Operator→KAI→Dynamo reduces version-matrix risk. Both now Apache-2.0 open source (checked in `nvidia/run-ai`, `nvidia/dynamo`), with a paid support-entitled Run:ai release if SLA is needed. |
| **Weaknesses** | Two heavy control planes added (Run:ai control plane + cluster services + Dynamo operator/planner/router) on top of Iris's existing five. Demonstrated patch burden: 7 carried Dynamo patches, prod pinned at Dynamo 1.4.2 / GPU Operator v25.3.4 vs upstream 1.6.0 / v26.7 — upgrades are already lagging. DGD breaks Lyceum's KEDA autoscaling and StatefulSet assumptions (operator special-cases, billing special-cases). Run:ai overlaps — not replaces — `deployment_controller`/Hydra policy, so ownership of placement must be renegotiated. |
| **Opportunities** | New DC is greenfield: define node pools (dedicated vs serverless), topology-aware placement across NVLink domains, and fractional GPUs for small/batch models from day one. Dynamo Planner could replace `deployment_scaler`'s hand-tuned HPA logic. Run:ai multi-cluster could later federate DC + cloud-burst (Verda/Atlas) under one quota view. |
| **Threats** | NVIDIA roadmap coupling: Dynamo/Run:ai/KAI/Grove moving parts (NATS/etcd vs K8s-discovery already a config fork in prod). Support boundary ambiguity between OSS and support-entitled releases during a 3 a.m. outage. Double-scheduler and double-autoscaler failure modes (KAI vs kube-scheduler; Planner vs KEDA/scaler) are exactly the class of bug that only appears under load. 8-GPU gang failures waste the most expensive resource first. |

## Lower-Complexity Alternative (test on the same EKS cluster, Phase 2b)

**Vanilla K8s + GPU Operator + Kueue + Dynamo-alone (or llm-d) + Gateway API Inference Extension.** No Run:ai control plane.

- **Scheduling/governance:** Kueue (CNCF, `ClusterQueue`/`Cohort` quotas, fair-sharing, preemption, topology-aware + all-or-nothing gang scheduling) — or KAI Scheduler *standalone* if fractional GPU is truly needed. One admission layer, GitOps-native CRDs, no separate UI/DB/control plane to HA.
- **Node supply:** Karpenter on AWS (just-in-time GPU nodes, consolidation); in the DC, the same Kueue policies over static owned nodes — which is all Run:ai would see there anyway.
- **Inference:** keep Dynamo (already integrated) but front it via GAIE (`InferencePool` + Endpoint Picker) so the routing layer is a Kubernetes standard, swappable to llm-d (v1.0, GAIE-native, prefix-cache routing + P/D disaggregation) without touching Iris. This keeps the option to exit Dynamo per-model.
- **Reliability parity:** PDBs (already built), multi-AZ system nodes, KEDA/HPA where it works today, proxy health registry (already built) — reliability at Lyceum lives in Iris, not in Run:ai's UI.
- **What you give up:** Run:ai's polished multi-tenant UI, fractional-GPU elasticity, and single-vendor support. What you gain: ~2 fewer control planes to upgrade, patch, and debug at 3 a.m.

Recommendation to test, not assume: if Phase-2 Step 4 shows KAI/Run:ai solving a placement problem Kueue cannot (measured GPU fragmentation on 8-GPU nodes), adopt Run:ai. Otherwise default to the lean stack for the DC and keep Run:ai as a Phase-2 multi-cluster option.

## Validation Plan

- **Functional:** OpenAI SDK smoke (chat sync/stream/tools, Responses API) against proxy FQDN; `lyceum infer deploy` lifecycle (create→running→scale→stop) with `deployment_replicas` rows as truth; Croesus balance delta matches token count.
- **Performance:** Phase-0 harness rerun per phase; report TTFT p50/p95, tok/s/GPU, cold-start (weights cached vs uncached) — same prompts, same model, no cherry-picking.
- **Reliability:** Phase-3 chaos script in CI against the test cluster; GPU-node cost guard: `gpu-8` node group returns to 0 within 15 min of test end (assert in Terraform/Karpenter TTL).
- **Cost ceiling:** budget alarm at the AWS account level; the 8-GPU node is the only line item that matters — everything else fits in the system nodes.

## Risks / Open Questions

- GPU SKU + interconnect in the new DC (H200 vs B200/B300, NVLink-only vs InfiniBand) — decides whether cross-node disaggregation/NIXL is even on the table; the AWS p4d/p5 test must not over-claim for a different fabric. **Needs your answer.**
- Run:ai OSS vs support-entitled release, and who is paged for KAI/Dynamo internals — **needs your answer** before Phase 1.
- Quota: AWS 8-GPU on-demand quota in the chosen region is the usual Phase-1 blocker; request it on day 1, design for `g6e`-only fallback.
- Rollback is trivial by construction: the test platform owns no production data; production Iris on GCP is untouched until the go/no-go.
